Lesson 2 · Fetching Data

How data gets from GitHub to the screen

You want to extend this app. The single most common thing you'll add is "fetch some new data and show it." By the end of this page you'll know the exact 3-layer path every fetch takes, the three caches that make it fast, and the copy-paste recipe to add your own.

~12 min · grounded in your real repo · pairs with the glossary

01The golden rule: the browser never calls GitHub directly

This is the thing to burn in. Your React components never talk to api.github.com. They talk to your own API routes, and those routes talk to GitHub. Every fetch passes through three layers:

runs in browser1 · The hooksrc/features/github/hooks/use-pr-files.ts
A TanStack Query hook. A component calls usePRFiles(org, repo, id) and gets back { data, isLoading, error }. It just fetch()es your own route — /api/github/.../files.
↓  fetch('/api/...') — your own server
runs on server2 · The API routesrc/app/api/github/prs/route.ts
Checks you're logged in, gets your token, checks the Redis cache, and only on a miss calls GitHub. This is where caching + rate-limit safety + "fan out across your linked accounts" lives.
↓  githubRequest() with your token
runs on server3 · The GitHub clientsrc/features/github/api/client.ts
One typed wrapper around fetch to api.github.com. Adds auth headers, tracks rate limits, does ETag conditional requests, follows pagination. Every GitHub call in the app goes through here.
Why this matters for extending: because every fetch follows the same shape, adding a new one is filling in a template — not inventing a new path. And your GitHub token never reaches the browser, so it can't leak. (see the real files cited above)

02The three caches (this is the "fast" secret)

GitReview is fast because the same piece of data is cached in three different places, each solving a different problem. Knowing which cache to reach for is half of "owning" the data layer.

Cache 1 · Browser

TanStack Query staleTime

Once a hook fetches the file list, the browser keeps it "fresh" for a while. Re-render, switch tabs and back — no new request. Default is 60s; per-hook it's tuned (e.g. CACHE_TTL_SECONDS.prFiles).

query-provider.tsx · use-pr-files.ts
Cache 2 · Server

Redis (stale-while-revalidate)

Your API route stores GitHub's answer in Redis. Fresh (<45s) → return instantly. Stale → return the old copy instantly anyway, and refresh in the background. The user never waits.

lib/redis/index.ts · api/github/prs/route.ts
Cache 3 · GitHub itself

ETag → 304 Not Modified

The client remembers GitHub's ETag (a version stamp). Next call sends If-None-Match. If nothing changed, GitHub replies 304 with an empty body — cheap, and it doesn't burn your rate limit.

api/client.ts · utils/etag-cache.ts
Analogy: three fridges at increasing distance. The browser fridge is in the room (instant). The Redis fridge is in the building (very fast). GitHub is the supermarket — and even there, the ETag is you asking "anything new since last time?" so you don't re-buy the same groceries.

03Stale-while-revalidate, in your actual code

This pattern (from api/github/prs/route.ts) is worth reading slowly — it's the heart of why the dashboard feels instant. Simplified:

// 1. Look in Redis
const cached = await redisGet(cacheKey);
if (cached) {
  const age = Date.now() - cached.ts;
  if (age >= SOFT_TTL_MS) {           // older than 45s = "stale"
    after(async () => {            // runs AFTER the response is sent
      const locked = await redisSetNX(lockKey, '1', 30); // single-flight lock
      if (!locked) return;          // someone else is already refreshing
      const fresh = await computePRPayload(userId);
      await redisSet(cacheKey, { payload: fresh, ts: Date.now() }, HARD_TTL);
    });
  }
  return NextResponse.json(cached.payload); // instant, even if stale
}
// cache miss: compute now, store, return

Two clever bits to notice — both things you'll want to reuse:

  • after(...) — Next.js runs this after the user already got their response. The refresh is free from the user's point of view.
  • redisSetNX lock — "set only if not exists." If 50 people hit a stale cache at once, only the first grabs the lock and refreshes; the rest skip it. This is called single-flight, and it stops 50 identical GitHub calls. (redisSetNX lives in lib/redis/index.ts)

04Built to not break (resilience)

Because the app leans on GitHub and Redis — things it doesn't control — the data layer is defensive. Three guards you should know exist:

GuardWhat it doesWhere
Circuit breakerIf Redis errors once, the app skips Redis entirely for 10s and runs cache-less instead of timing out on every request.lib/redis/index.ts
Graceful no-opNo REDIS_URL set (e.g. local dev)? Every cache call quietly returns "miss." The app still works, just slower.lib/redis/index.ts
Rate-limit trackerReads GitHub's rate-limit headers off every response. If you're out of budget, it throws 429 early instead of getting you blocked.utils/rate-limit-tracker.ts
Extender's note: these guards live inside the shared helpers (redisGet, githubRequest). So if you add new data fetches using those helpers, you get all this resilience for free. Don't call fetch('https://api.github.com/...') directly — you'd lose every guard above.

05🛠 Recipe: add a brand-new data fetch

This is the payoff for "own & extend." Say you want to show a PR's commit list. You'd add four small pieces, following the existing pattern exactly:

  1. The GitHub call — add listPRCommits(token, ...) in src/features/github/api/ (next to pulls.ts), using githubPaginatedRequest() so you get pagination + ETag + rate-limit for free.
  2. The API route — add src/app/api/github/.../commits/route.ts. Copy the shape of prs/route.ts: auth() → check Redis → call your new function → cache the result.
  3. The query hook — add usePRCommits(...) in src/features/github/hooks/, copying use-pr-files.ts. Give it a unique queryKey like ['pr-commits', org, repo, id].
  4. Use it — call const { data } = usePRCommits(...) in a component and render. Done — caching, loading, retries, resilience all handled.

Notice the symmetry: api fn → route → hook → component. Once you see it, every data feature in the app is the same four-step shape.

06Check yourself

1. A React component needs the list of changed files. Who does it ask?
2. The Redis copy is 2 minutes old (stale). What does the API route do?
3. You're adding a new fetch. Why use githubRequest() instead of plain fetch() to GitHub?
Scenario: the dashboard shows slightly old PR counts for a few seconds after someone opens a new PR. Bug or design?

It's design — stale-while-revalidate. The first load after the soft TTL serves the cached (slightly stale) copy instantly and kicks off a background refresh. The trade-off is "instant but up to ~45s old" instead of "always fresh but slow." If you ever need strictly-fresh data, you'd lower SOFT_TTL_MS or bypass the cache for that route.
