Lesson 1 · The Big Picture

What GitReview is, in one mental model

By the end of this page you'll be able to explain — in plain words — what every major piece of your app does, and trace exactly what happens when someone opens a pull request.

~8 min · grounded in your real repo · open the glossary alongside this

00The one-sentence version

GitReview is a website that makes reviewing big GitHub pull requests bearable. GitHub's own review page chokes on large PRs — hundreds of files, a sluggish diff, lost context. GitReview re-renders that same data in a faster, smarter interface: a categorized file tree, diffs that stay smooth at any size, and a Gemini AI assistant on every screen. (source: your README.md)

Analogy: Think of GitReview as a better pair of glasses for GitHub. The data still lives on GitHub. GitReview borrows it (with your permission), arranges it so your eyes don't hurt, and writes any comments back to GitHub where your team expects them.

01The 9 building blocks (and why each was picked)

Every modern web app is just a handful of jobs. Here are GitReview's nine, each with the tool that does the job and the one reason it was chosen. Don't memorize — just get a feel for the shape.

The frame

Next.js 16 next · App Router

Runs both the server and the browser code in one project. Folders become URLs. Chosen so the first paint can be server-rendered (fast) while still being interactive.

The language

TypeScript typescript (strict)

JavaScript with types. Catches mistakes before they ship. "strict" mode means no lazy shortcuts.

The login

NextAuth v5 next-auth · GitHub OAuth

"Sign in with GitHub." Handles the whole login dance and stores your access token. Chosen because the app's data is GitHub data.

The data source

GitHub REST API fetch

Where PRs, files, diffs and comments come from. GitReview is a polished reader/writer on top of it.

The fast copy

Upstash Redis ioredis

A speed cache. Instead of asking GitHub the same thing repeatedly, answers are kept here for minutes. Chosen for "instant feel."

The records

Neon Postgres drizzle-orm

The real database — review sessions, which files you've viewed, AI chats, linked accounts. Drizzle talks to it type-safely.

Browser data

TanStack Query @tanstack/react-query

Fetches & caches data in the browser so components just ask for "the PR files" and don't juggle loading flags.

The smooth diff

Virtual + Shiki @tanstack/react-virtual · shiki

Virtual draws only on-screen lines; Shiki colors the code (VS Code's engine). Together: huge diffs stay smooth & readable.

The assistant

Gemini @google/generative-ai

The AI bar. Explains code, summarizes changes, spots bugs — streaming answers token by token.

Two more quiet helpers: Zustand (zustand) is the shared whiteboard that lets, say, the file tree tell the diff viewer "this file is now selected"; and shadcn/ui + Tailwind v4 are the look — pre-built, restyleable components plus utility CSS. (source: package.json, README.md stack table)

02The journey of opening a pull request

This is the single most useful thing to understand. Follow one click — opening /twofourlabs/app-kavana/pull/255 — all the way through. Each step says where it runs. (source: the Data Flow section of your ARCHITECTURE.md)

SERVER
The URL becomes a page. The folder app/(app)/[org]/[repo]/pull/[id]/ matches the address. The layout.tsx reads the pieces: org, repo, id = 255.
SERVER
Fetch the PR's basic info. It first checks the Redis cache. Cache hit → instant. Cache miss → call the GitHub API, then save the answer in Redis for ~5 min. The PR title/author/status are baked straight into the HTML.
BROWSER
The page comes alive (hydrates). Now interactive code takes over. It finds or creates your review session (so it remembers your progress) via /api/review-sessions.
BROWSER
Load the file list. TanStack Query asks the app's own API for the changed files, already categorized into a tidy tree, and shows it in the left sidebar.
BROWSER
You click a file. That writes activeFilePath into the Zustand store — the shared whiteboard everyone watches.
BROWSER
Load that file's diff. Another TanStack Query call fetches the diff, already parsed into hunks (blocks of changed lines).
BROWSER
Render it smoothly. TanStack Virtual draws only the lines on screen; Shiki colors the code lazily, per language. A 5,000-line file feels like 50.
The key insight: work is split in two. The server does the first, heavy load so the page shows up fast. The browser handles everything interactive after that. Redis makes the server fast; TanStack Query + Virtual + Shiki make the browser fast.
